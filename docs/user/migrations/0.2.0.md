# Upgrade to 0.2.0

From 0.1.2 · 2026-10-01 · [all guides](./index.md)

0.2.0 makes flow judge every change a tool call makes to the tree, not only the changes the Edit and Write tools make. A change a shell command, an MCP tool or a subagent makes is checked after it lands, and a refused change is put back. The hook registrations change to make that work, so every repo re-runs `flow init`. A repo that overrides `docs.noMarkdownInUserDocs` must remove the override, and a repo with its own `banCommands` rule about heredoc text must set `matchHeredocs: true`.

## 1 · Install 0.2.0

```sh
npm i -D @jawache/flow@0.2.0    # when flow is a dev dependency of the repo
npm i -g @jawache/flow@0.2.0    # when `flow` is installed globally
```

## 2 · Required changes

### 2.1 · Re-run `flow init` to update the hook registrations

**Applies if:** after the install, `flow status` prints a red `hooks:` line that says one or both of these:

- `does not call flow for PostToolUseFailure — re-run flow init`
- `calls flow for PostToolUse on some tools only — an older flow registered it that way`

Every repo upgrading from 0.1.2 has both.

**Change:** run `flow init` in the repo. It keeps the existing `flow.config.ts` and `.githooks/pre-commit`. In the Claude Code settings file it widens the `PostToolUse` registration to every tool, and adds `PostToolUseFailure`. The settings file is the user-level one, `~/.claude/settings.json`, or `$CLAUDE_CONFIG_DIR/settings.json` when that variable is set. It is not the repo's `.claude/settings.json`. Afterwards flow's five registrations are:

```json
"SessionStart":       [{ "matcher": "startup|resume|clear|compact", "hooks": [{ "type": "command", "command": "flow hook session-start" }] }],
"PreToolUse":         [{ "matcher": "*", "hooks": [{ "type": "command", "command": "flow hook pre-tool-use" }] }],
"PostToolUse":        [{ "matcher": "*", "hooks": [{ "type": "command", "command": "flow hook post-tool-use" }] }],
"PostToolUseFailure": [{ "matcher": "*", "hooks": [{ "type": "command", "command": "flow hook post-tool-use-failure" }] }],
"Stop":               [{ "hooks": [{ "type": "command", "command": "flow hook stop" }] }]
```

If the settings file does not parse (a comment or a trailing comma), `flow init` writes nothing to it and says so. Fix the JSON and run `flow init` again.

Restart any Claude Code session that was open during the upgrade. A tool call that started under the old version prints one `flow — could not see what this call changed` message when it finishes.

**Why:** flow now takes a snapshot of the tree before every tool call and compares it after, so it needs the after-call hook for every tool, including calls that fail.

### 2.2 · Remove any override of `docs.noMarkdownInUserDocs`

**Applies if:** `grep -rn "noMarkdownInUserDocs" flow.config.ts` (and your own pack files) prints a line. After the install, `flow status` reports `unknown-entry` for it, and the config does not load. While it does not load, flow refuses every write except a write that fixes the config.

**Change:** delete the `override(docs.noMarkdownInUserDocs)` line. The `docs` pack no longer refuses markdown under `docs/user/`. To keep refusing it, add the entry to your own pack. This is the entry 0.1.2 shipped, with a shorter message:

```ts
noMarkdownInUserDocs: guardrail()
  .at(write, commit)
  .on("docs/user/**/*.md", "docs/user/**/*.mdx")
  .check(protectedPath({}))
  .message("User docs are HTML. Markdown belongs in docs/agent/.")
  .test({ block: [{ path: "docs/user/guide.md", content: "# hi" }] }),
```

**Why:** user docs may now be markdown. A repo that bound `docs` without an override loses the refusal with no error.

### 2.3 · Set `matchHeredocs: true` on a `banCommands` rule about heredoc text

**Applies if:** the repo has its own `banCommands` rule whose patterns must match text a command is fed through a heredoc, such as a commit message. `flow test` reports a failing `block` case where the banned text appears only inside a heredoc.

**Change:**

```ts
// before
banCommands({ ban: ["…"] })
// after
banCommands({ ban: ["…"], matchHeredocs: true })
```

**Why:** `banCommands` now leaves heredoc bodies out of the text it matches, so a script that only contains the words of a banned command is not refused. A heredoc fed to a shell (`bash`, `sh`, `zsh` or `eval`) is still matched. The shipped `git.noAiAttributionInCommits` and both `noShellSubstitutionInProse` entries already set it.

### 2.4 · Clear a red `snapshot:` line

**Applies if:** `flow status` prints a red `snapshot:` line saying a rule `guards <path>, which git ignores`.

**Change:** list the path's glob in `snapshotInclude`, the second argument to `defineConfig`, or narrow the rule with `.on(…)` or `.ignore(…)`:

```ts
export default defineConfig([pack(house)], { snapshotInclude: [".env"] });
```

**Why:** the snapshot records the files git lists, tracked or untracked, so a shell write to a path git ignores is never detected unless `snapshotInclude` lists it. `secrets.envEncrypted` on a gitignored `.env` file is the usual case.

## 3 · What now blocks or passes differently

- **Shell commands, MCP tools and subagents are checked.** A write or delete rule now runs on a change any tool call makes: a heredoc, `sed -i`, a script, a formatter, a code generator, `npm install`. A refused file is put back, under `flow — write reverted after it landed` or `flow — delete reverted after it landed`. If a rule refuses generated output or a tool's own files, narrow it with `.ignore(…)`. Keep build output, logs and caches in paths git ignores.
- **A background command's later writes are judged.** A write a background process makes after its tool call returns is judged by the next tool call and put back if refused.
- **`rm x && cat > x` is judged as a write** of `x`, not only as a delete.
- **`banCommands` leaves heredoc bodies out** unless the rule sets `matchHeredocs: true` (2.3). The shipped force-push ban, the justfile recipe map and the work pack's rules now let heredoc text through.
- **A heredoc is the commit message only when the commit reads standard input**, with `-F -` or `--file=-`. `commitReason` and the git pack's message rules no longer check `git commit <<EOF` without `-F -`. Commit with `git commit -F - <<'EOF'`.
- **A breadcrumb is shown for a file a shell command reads.** `cat`, `head`, `sed -n`, `grep`, `rg`, `find`, `ls`, `<` and a git pathspec count as reads, and the note is shown before the command runs. A refused command shows no notes.
- **A folder that is not a git checkout is refused on every tool call**, because flow has nothing to take a snapshot with. Run `git init`, or remove `flow.config.ts` from a folder that is not a repo.
- **`flow status` and `flow facts` read transcripts from `$CLAUDE_CONFIG_DIR/projects`** when that variable is set.
- **Shipped text changed:** the `flow` pack's orientation note, and the `docs` pack's messages, which now say user docs may be HTML or markdown.

## 4 · Optional

- **Let only named agents write:** `oneWriter({ writers: [...] })` refuses a write or delete by a session that has none of the listed categories. `pack(work, { writers: ["builder", "parent"] })` turns it on for the `work` pack. Test cases accept `actor: [...]`.
- **Choose what a refusal puts back:** `defineConfig([...], { revert: "all" })` puts back every file the refused call changed. The default, `"refused"`, puts back only the refused files.
- **`flow status`** shows the live session's permission mode. **`flow facts`** counts shell reads and writes, and calls per mode.

## 5 · Verify

```sh
flow status    # green, with: ✓ hooks: … SessionStart · PreToolUse · PostToolUse · PostToolUseFailure · Stop
flow test      # every case green
flow commit $(git ls-files --cached --others --exclude-standard)    # exit 0
```
